# Implementation Plan

> Sequencing precondition: this plan builds on the implemented workout-docs and
> route-maps specs — the sync engine's per-file pipeline, content-hash dedupe
> against the archive, per-file failure isolation, the settings-file reader
> pattern, the data-root layout, and the CLI shell with its 0/1/2 exit-code
> contract must be in place before these tasks start. No task modifies the
> per-file pipeline, explicit-source sync, regen, or load.
>
> Two further preconditions come from the Phase 3 sequencing:
>
> - **settings-foundation** (pre-wave, direct implementation) must have landed.
>   It provides the shared settings-file location in the layout leaf and a
>   single reader that parses the data root's settings file once, raising one
>   shared settings error for file-level problems. No task here adds the
>   settings filename to the layout, adds another parser, or modifies the tile
>   settings reader — the inbox table reader is a typed projection over the
>   already-parsed mapping.
> - **wiki-contract** must have landed. It provides the ownership-declaration
>   refresh this plan wires into the drain, the published ownership contract
>   (tool-owned state plus the clause for user-configured locations fitdocs may
>   create) these tasks conform to, and the document-format-version gate that
>   skips a newer document *without archiving it* — which is why the move
>   disposition here keys on archive presence and never on a skipped label.
>
> One landing-order assumption: **plugin-api's** sync-command wiring lands
> before task 4.2, which edits the same region of the CLI.

  - Typed settings covering the inbox path, the settle interval, additional ignore patterns, the disposition, and the processed-files destination, with disposition modeled as a closed two-member choice so deletion is unrepresentable
  - Loud validation raising the typed settings error, each message naming the file and offending key: a non-string or empty path or destination, a settle interval that is not a non-negative real number (a boolean is rejected explicitly), a non-list-of-strings ignore value, an unknown disposition, the move disposition without a destination, and a destination equal to or nested inside the resolved inbox

- [x] 2. Ingestion policy and quarantine state
- [x] 2.1 Implement candidate selection with the ignore policy
  - Recursive discovery of regular files with the fit extension matched case-insensitively, returned in a deterministic order sorted by inbox-relative path, alongside the inbox-relative label every report entry uses
  - Exclusion rules: any candidate whose inbox-relative path has a component beginning with a dot; the default junk-name patterns; and any additional configured patterns, applied on top of rather than instead of the defaults
  - Pattern matching against both the basename and the inbox-relative path, case-normalized so behavior is identical on case-sensitive and case-insensitive filesystems
  - Ignored files are simply not candidates — they never reach processing and never appear in any report channel, and selection only reads the inbox
  - Observable: unit tests confirm nested discovery order, uppercase-extension inclusion, non-regular-file exclusion, dot-component exclusion including hidden companion files and hidden subdirectories, each default pattern, additive configured patterns, and that ignored files appear in no output
  - _Requirements: 3.1, 3.2, 3.3, 3.4, 3.5_
  - _Boundary: CandidateSelector_
  - _Depends: 1.2_
- [x] 2.2 Implement the batched stability check
  - Observe every candidate, wait one settle interval, then observe every candidate again: a candidate is stable when both observations succeed and report identical size and modification time, and is otherwise deferred with a human-readable reason naming the file
  - Exactly one wait per drain regardless of candidate count, performed through an injected sleep so tests spend no wall-clock time; a settle interval of zero performs no wait and admits every candidate that can be observed
  - The check is stateless — nothing about a deferral persists — and deferred files are left completely untouched and never opened
  - The shared inbox note value is introduced here for use by the deferred, quarantined, and failed-move channels, with its two fields named for the agreed report-type convention — the subject it concerns and the detail explaining it — and no optional remedy field, since every note this feature produces is actionable from its detail; the already-shipped warning and report types are not renamed
  - Observable: unit tests confirm stable and changed and vanished outcomes, the zero-interval bypass, and exactly one sleep call for a batch of many candidates
  - _Requirements: 4.1, 4.2, 4.3, 4.4, 4.5_
  - _Boundary: StabilityCheck_
- [x] 2.3 Implement the leave-in-place and move dispositions
  - Leave-in-place is a no-op by construction: nothing touches the inbox file, and re-drains skip it because its content is already archived
  - The move disposition relocates a file out of the inbox to the configured destination, preserving its inbox-relative subpath and creating parent directories on demand, using a move that works across volumes since the inbox commonly lives on different storage from the data root; deciding *whether* a file is eligible belongs to the caller (task 3.3), so this component only ever handles files already confirmed archived
  - Collision-safe naming: when the destination path already exists, the file is stored under a distinct content-derived name, escalating deterministically until a free name is found, so both files survive and nothing is ever overwritten
  - No code path deletes an inbox file under any configuration; a move failure returns a note rather than raising, leaving the file in place for a later drain to retry
  - Observable: unit tests confirm subpath preservation with parent creation, a collision producing a distinct name with both files intact, repeated collisions escalating deterministically, and an unwritable destination returning a note instead of raising
  - _Requirements: 6.1, 6.2, 6.3, 6.5, 6.6_
  - _Boundary: Disposition_
- [x] 2.4 (P) Implement the quarantine record store
  - A content-keyed record of files that could not be processed, stored under the data root's tool-state directory: each entry carries the content hash, the inbox-relative name last seen, and the recorded failure reason
  - Following the established data-root state-file contract: an absent record yields an empty record and never creates the file or its parent directory, while a record that exists but is not parseable or is not in the documented shape raises the typed quarantine error naming the file rather than being discarded or rebuilt
  - The tool-state directory does not exist in a fresh data root and the layout leaf performs no I/O, so this store creates that parent directory on demand at save time
  - Membership and mutation are keyed on content, never on names; mutators return copies rather than mutating in place, and entries are serialized in a stable order sorted by hash
  - The record carries no timestamp or other clock-derived value, and saving is atomic and write-if-different: an unchanged record leaves the file byte-identical and performs no write
  - Independent of tasks 2.1 through 2.3 — a separate module depending only on the layout additions from task 1.1
  - Observable: unit tests confirm absent-yields-empty with nothing created, a first save into a data root with no tool-state directory succeeding, round-trip with stable ordering, malformed record raising, membership matching by content while a same-named different file misses, and saving an unchanged record writing nothing
  - _Requirements: 5.1, 5.4, 5.6, 7.4_
  - _Boundary: QuarantineStore_
  - _Depends: 1.1_

- [x] 3. Drain orchestration in the sync engine
- [x] 3.1 Add the drain entry point and its report composition
  - A third engine entry point beside sync and regen that composes inbox policy around the existing per-file pipeline without modifying any pipeline stage: select candidates, settle them, read and hash each stable candidate, then process admitted files through the same isolated per-file call sync already uses, with the same source-label convention so report entries name inbox-relative paths
  - The hash read doubles as a readability probe: a candidate that observes as stable but cannot be read is deferred with its reason, never failed and never quarantined, so an unmaterialized cloud placeholder is a timing outcome rather than a permanent verdict about the file
  - A drain report composing the unchanged sync report with the drained inbox path and the deferred channel, so the existing report type and its meaning are untouched; every admitted file still lands in exactly one of written, skipped, or failures, ignored files appear nowhere, and only failures drive the failure outcome
  - Wire the ownership-declaration refresh into the drain: the drain calls it once per run, in the same position and with the same handling the explicit-source sync uses, so foreign declarations become warnings rather than errors. This is a wiki-contract integration obligation, not an optional extra — wiki-contract wires only sync and regen, and the drain becomes the primary ingestion path, so without this the declaration would silently stop being emitted and refreshed for most users
  - Observable: integration tests cover an empty inbox, an ignored-only inbox, a mixed drain classifying files exactly as an explicit-source sync would, a deferral including the unreadable-file case, a report naming the drained inbox path, and a drain emitting the ownership declaration into a data root that lacks one while refreshing a stale one — matching the outcomes an explicit-source sync produces
  - _Requirements: 2.1, 2.3, 2.4, 3.5, 4.2, 4.6, 7.1, 7.6_
  - _Boundary: DrainOrchestration, DrainReport_
  - _Depends: 2.1, 2.2_
- [x] 3.2 Add quarantine partitioning, recording, and retry to the drain
  - Stable candidates whose content hash is already recorded are not re-processed and are reported in their own channel with the recorded reason
  - Quarantining is narrowed to source-level faults — the file's own bytes cannot be decoded or parsed — because the record is keyed by content hash and is only meaningful for faults that are a property of those bytes. A failure that is a property of the existing document, damaged preserved regions being the representative case, is reported as a failure with its reason and is deliberately not recorded, so repairing the document is enough to make the next drain succeed without any retry flag
  - The level test is a single predicate over the failure's type that defaults to not recording: an unrecognized fault is loud on every run rather than silently remembered
  - The retry option re-attempts recorded files: a success removes the entry, a renewed failure replaces it and is reported as a failure; the force option governs archive-skip policy only and never implies retry
  - The record is evolved in memory during the drain and persisted once at the end, only when it changed
  - Observable: integration tests confirm a first source-level failing drain creates an entry and fails, the following drain reports that file quietly and succeeds, a document-level failure fails the run while leaving no entry behind and succeeds on the next drain once the document is repaired, a renamed copy of a recorded file is still recognized while a same-named different file is treated as new, and retry both clears and updates entries
  - _Requirements: 5.1, 5.2, 5.3, 5.4, 5.5, 5.7, 7.4_
  - _Depends: 2.4, 3.1_
- [x] 3.3 Add disposition gating and the moved and failed-move channels
  - Disposition is gated on a positive, filesystem-checked condition: a file is moved only when its content is present in the archive once its processing has finished. It is never gated on a skipped label. Written files pass because the archive copy is the pipeline's last write, and content-dedupe skips pass because being already archived is what made them skips
  - This matters because the document-format-version gate skips a document written by a newer fitdocs and deliberately archives nothing, so that the next run retries the source. Moving such a file out of the inbox on the strength of its skipped label would orphan it un-ingested in the processed directory and permanently defeat that retry, silently. Gating on archive presence also makes the guarantee hold for any future skip reason that archives nothing
  - Failed, deferred, and quarantined files never reach the gate at all
  - The moved and failed-move channels join the drain report; a failed move leaves the completed processing intact, leaves the file in the inbox, and never changes the classification or the failure outcome. Failed moves stay a separately named channel — not folded into failures, which they are not, nor into moved, which they did not — so downstream documentation and the packaged agent skill can enumerate every reported channel by name
  - Observable: integration tests confirm leave-in-place leaves the inbox byte-identical after a successful drain; move relocates only files whose content is archived; failed, deferred, and quarantined files stay in the inbox; a failing move is reported in its own channel while the run still succeeds; and — asserted on filesystem state rather than report labels — a document at a newer document-format version is skipped with a warning, nothing lands in the processed directory for it, the file stays in the inbox, the next drain still finds it as a candidate, and it is moved only once a drain actually archives it
  - _Requirements: 6.2, 6.4, 6.5, 7.5_
  - _Depends: 2.3, 3.1_

## Implementation Notes
- 1.1: The tool-state directory constant already exists as `layout.TOOL_STATE_DIR` (wiki-contract `49752ef`) and `OWNED_PATHS` already composes its entry from it. Consume `TOOL_STATE_DIR`; do NOT add a second `STATE_DIR` constant. design.md was corrected to match.
- 1.2: `inbox.py` imports `SettingsError` from `fitdocs.settings` despite design.md's "does not import fitdocs.settings" line — reconciled under design.md's adaptation clause, matching the shipped `TileSettingsError`/`PluginSettingsError` precedent. The file-vs-table error split stays real because the CLI catches `SettingsError` and exits 2 for both. The containment check (processed_dir inside inbox) lives in `load_inbox_settings` and is purely lexical (`os.path.normpath`, no filesystem access) — task 1.3's `prepare_inbox` must not duplicate it.
- 1.3: `prepare_inbox` is two-phase — both paths are validated before either is created, so a refusal leaves the filesystem untouched. Resolution is lexical (`os.path.normpath`) and reuses task 1.2's `_resolve_inbox_relative`; do not introduce a second normalization.
- 1.3 (carry to task 4.2, CLI wiring): a `mkdir` failure inside `prepare_inbox` leaks a raw `PermissionError` / `NotADirectoryError` / `FileExistsError` (dangling symlink) instead of the typed `InboxSettingsError`, so it would bypass the CLI's `_config_error` path and surface as a traceback. design.md's Error Handling table is silent and the codebase precedent is uniformly bare `mkdir` (`sync.py:900/903/907`, `tiles.py:424`, `declaration.py:405`), so this was deliberately not fixed in 1.3. Decide in 4.2 whether the pre-flight should wrap it.
- 1.3 (carry to task 5.2, suite hygiene): `prepare_inbox`'s `data_root_norm = Path(os.path.normpath(data_root))` is load-bearing but pinned by no test — `config.resolve_data_root` returns the data root unnormalized, so `FITDOCS_DATA=/path/sub/..` would spuriously refuse an inside-the-root inbox without it. Add a test passing a data root containing a `..` component.
- 1.3: symlink escape is deliberately out of scope for `prepare_inbox` — resolution is lexical by design (design.md Security Considerations), and Req 1.6's threat model is typos and unmounted cloud storage, not an adversary. wiki-contract's symlink fix (`9a61cb5`) was scoped to document reads.
- 2.1 (ESCALATE — design question for the human, not a code defect): all four `DEFAULT_IGNORE_PATTERNS` entries are structurally unreachable through a real candidate walk. Reaching the pattern check requires a basename ending in `.fit`, which can never also end in `.tmp` or `.part`; `.syncthing.*` and `.DS_Store` are dot-prefixed and always caught by the Req 3.2 dot-component rule first. The implementation is faithful to design.md as written, and the patterns are pinned by direct `_matches_any_ignore_pattern` tests plus a set-membership test — but Req 3.3's defaults currently exclude nothing in practice. If a partially-written `run.fit.tmp` should be ignorable, the `.fit` predicate (not the pattern list) is what would need to change. Configured `ignore` patterns from Req 3.4 ARE reachable and do work.
- 2.1: `_ignore_patterns` composes `DEFAULT_IGNORE_PATTERNS + settings.ignore` (additive, never replacing) and is on the live `select_candidates` path — verified by call-site mutation. Pattern matching is case-normalized against both basename and inbox-relative POSIX path.
- 2.2 (PROCESS — applies to every future task in this repo): mutation-testing a module by rewriting it repeatedly within the same second reuses the stale `__pycache__` `.pyc` (CPython validates on mtime-seconds + size), so pytest silently runs the PREVIOUS variant and reports false SURVIVED/CAUGHT results. Always `rm -rf src/fitdocs/__pycache__ tests/__pycache__` before each mutant and run pytest with `PYTHONDONTWRITEBYTECODE=1`. This produced a wrong mutation claim in 2.2 round 1.
- 2.2: `settle(candidates, *, settle_seconds, sleep=time.sleep) -> SettleResult`. Observation is `stat`-only — no candidate is ever opened. `InboxNote(subject, detail)` has exactly two fields and no remedy field; it is the shared note type for the deferred, quarantined, and failed-move channels. `SettleResult(stable, deferred)` preserves input order on both tuples.
- 2.2: the `sleep=time.sleep` default is bound at def time, so it cannot be pinned by monkeypatching `time.sleep` after import — the test asserts `inspect.signature(settle).parameters["sleep"].default is time.sleep` instead. Adjudicated correct by review; do not "fix" it into a behavioral test.
- 2.3: `move_processed(candidate, processed_dir, sha256) -> str | InboxNote`. Uses `shutil.move` (cross-volume safe — a plain `Path.rename` fails with EXDEV, and the inbox commonly lives on different storage). Collision naming is `<stem>-<sha256[:8]><suffix>`, then `-2`, `-3`, escalating deterministically; nothing is ever overwritten. A failure returns an `InboxNote` and leaves the source in the inbox.
- 2.3: design.md's `move_processed` postcondition originally said the return was "relative to the data root when nested under it, else absolute", which is unsatisfiable — the signature carries no `data_root`. design.md line 542 was amended to specify the absolute path; the caller (`drain`) relativizes for presentation if needed. Nothing downstream needs it: Req 7.1 gives per-file detail only to the deferred, quarantined, and failed-move channels, while `moved` is a count row.
- 2.3 (PROCESS): four consecutive tasks in `src/fitdocs/inbox.py` (1.3, 2.1, 2.2, 2.3) were rejected for the SAME defect class — a docstring, module-level or test-level, claiming a guarantee the code or the assertions could not deliver. When adding a slice to this module, update the whole docstring frame (slice count, the "later tasks" list, and the write-surface sentence), and make every test docstring state only what its assertions prove.
- 2.4: `load_quarantine` / `save_quarantine` over `<data-root>/.fitdocs/quarantine.toml`. Absent yields an empty record and creates nothing (not the file, not the parent). Unreadable (`OSError`), unparseable TOML, wrong-shape entries, and duplicate `sha256` keys all raise `QuarantineError` naming the file — never rebuilt or discarded. Saving is atomic (`tempfile.mkstemp` + `os.replace`) and write-if-different, returning whether it wrote; `.fitdocs/` is created on demand at save time because `layout` is I/O-free.
- 2.4: there is no shared atomic-write helper in this repo — `tiles._write_through`, `load.engine._atomic_write`, and `load.profile.save_profile` are three private local copies, and `quarantine.py` is a fourth. Consistent with precedent; consolidating them is out of scope for this spec.
- 2.4 (carry to task 3.2 or 4.2, both optional): `quarantine.py:151`'s `path.is_file()` sits outside the `try`, so a non-traversable `.fitdocs/` directory raises a raw `PermissionError` rather than `QuarantineError` — same Req 5.6 clause, one line earlier. Realistic unreadable-*file* case is fixed and tested; this residual matches `athlete.py` and `load/profile.py`. Also: no test loads a hand-written out-of-order record, so the defensive load-time sort at `:179` is unpinned (the code is correct).

- 3.1: `drain()` also runs `_scan_symlinked_documents(data_root)` for parity with `sync`/`regen`. This is beyond the inbox spec's Req list, is documented as such in `drain()`'s docstring, and is pinned by its own test.
- 3.1: `DrainReport.quarantined` / `.moved` / `.move_failures` are declared with the design's types but are always `()` until tasks 3.2/3.3 populate them. `drain()` accepts `quarantine`, `processed_dir`, and `retry_quarantined` to match the design signature but does not consult them yet — remove those "not yet consulted" docstring lines as each channel gains meaning.
- 3.2 (ESCALATE — design decision for the human): design.md says the quarantine level test is "a single predicate over the failure's exception type (`is_source_level`)". That is not implementable as written: `FileFailure` carries only `source: str` and `reason: str`, `_reason` renders `type(exc).__name__` into a *string*, and `_process_isolated` binds and discards the exception — and `_process_isolated` must stay byte-unchanged for Req 7.3. String-matching the reason was tried and is wrong (misses `NotFitFileError` and `FitIntegrityError`). The implementation therefore re-derives the level by re-parsing the already-in-memory probe bytes. Consequences: (a) `is_source_level`'s `RegionError` branch is unreachable from `drain` — a wholly wrong predicate changes no drain behavior, only a unit test catches it; (b) one real divergence exists — if `_process_file`'s own read raises `OSError` after the probe read succeeded (file removed in between) over undecodable bytes, the fault is recorded with an `OSError` reason, which a true type predicate would never do. The clean alternative is an optional keyword-only observer on `_process_isolated` (e.g. `on_exception: Callable[[BaseException], None] | None = None` called from both except blocks), which keeps explicit-source behavior byte-identical and still satisfies Req 7.3 as written, but changes a frozen function. Decide: accept the re-parse, or adopt the observer parameter.
- 3.2: the sha256 is computed from `drain()`'s existing probe read — there is no second read for hashing. The pipeline's own `_process_file` read is the double read design.md explicitly accepts.
- 3.2: `is_source_level` is `isinstance(exc, FitDecodeError)`; `errors.py` defines exactly `FitDecodeError`, `NotFitFileError`, `FitIntegrityError`, so the subclass check covers design.md's "decode/integrity errors" with nothing missed. It defaults to NOT recording, so an unrecognized fault is loud every run.
- 3.2: the quarantine record is evolved in memory across candidates within one drain (two candidates sharing bad content: the first fails and records, the second is reported as quarantined against that just-added entry) and persisted once at the end only when changed. `save_quarantine` short-circuits on identical bytes, so an mtime check alone cannot prove "no write" — the suite uses a spy on `fitdocs.sync.save_quarantine` asserting zero calls.
- 3.2 (PROCESS): a reviewer's pristine baseline copy in the shared scratchpad was overwritten mid-review by another agent's tooling, briefly making a changed file look unchanged. Reviewers should write baseline snapshots to a uniquely-named subdirectory and treat an apparently-unchanged baseline after a known edit as suspect.
- 3.3: the disposition gate is `not failed_this_candidate` AND archive-presence AND `Disposition.MOVE` AND `processed_dir is not None`. **All four clauses are load-bearing — do not "simplify" any of them.** In particular `not failed_this_candidate` looks redundant under archive-last write ordering but is NOT: with `force=True`, `_process_file`'s dedupe short-circuit (`if archive.exists() and not force:`) is bypassed, so already-archived content is re-processed and can fail with a `RegionError` while its content sits in the archive. Dropping the clause then moves a FAILED file out of the inbox, violating Req 6.4. Pinned by `test_forced_reprocessing_failure_on_already_archived_content_is_not_moved`, which is proven non-tautological by differential force=True/force=False execution.
- 3.3: `drain()` has two deferral paths — settle-deferral and the read-failure (`except OSError`) probe branch. Both must stay clear of the disposition gate; both are now pinned.
- 3.3: the drain reports the *renamed* destination in `moved` when `move_processed` resolves a collision. `move_processed` never re-hashes; `shutil.move` may copy bytes across volumes, but the drain never reads a candidate a second time.
- 4.1: `_report_drain(report, *, command)` renders all EIGHT count rows unconditionally (written, skipped, failed, warnings, deferred, quarantined, moved, move failures) — even at zero — because downstream consumers enumerate channels by name. Detail *listings*, by contrast, print only when non-empty, following the existing `_report` convention. Both halves of that split are pinned by tests.
- 4.1 (TESTING TECHNIQUE — reuse for any rendered-output assertions): substring-anywhere assertions (`assert "Quarantined" in output`) CANNOT distinguish a table row from a detail heading, and let a table with two "Deferred" rows and no "Quarantined" row pass. `tests/test_cli_drain_report.py` has `_table_region` / `_row_count` / `_body_row_count` / `_block` helpers that scope assertions to the box-drawn table region and to per-heading blocks. They fail LOUDLY (`StopIteration` / `IndexError`) on a parse miss rather than silently returning empty, which is what keeps them from going vacuous. Use distinct counts per channel so cross-wiring shows as a wrong number.
- 4.1: markup/truncation safety uses the existing `markup=False` + `soft_wrap=True` convention (rich treats `[` as a markup tag and hard-wraps at width 80). Pinned by a bracketed-path test and a 300-char test.
- 4.1: `tests/test_cli_drain_report.py` names `_PRE_TASK_CLI_COMMIT = "faa6d09"` deliberately — Req 7.3 requires `_report` to match its *pre-inbox-feature* state permanently, so a dynamic HEAD lookup would compare against a commit that already contains this feature and be tautological. The baseline source itself is vendored at `tests/fixtures/report_baseline_faa6d09.py` (not fetched from git history at test time): a depth-limited clone doesn't carry the `faa6d09` object, which previously turned a green-tree CI checkout into a `CalledProcessError` on missing git plumbing rather than a report of drift in `_report` (`.kiro/queue/2026-07-26-git-resolved-commit-pins-in-tests.md`). This trades provable-against-history for provable-against-a-recorded-baseline that a future edit could tamper with; the test still asserts the extracted baseline `FunctionDef` is non-`None` so a missing/corrupt fixture fails loudly rather than passing vacuously.
- 4.2: `sync_command`'s `SOURCE` is now optional. `_inbox_preflight` runs the ordered pre-flight (settings parsed once -> `[inbox]` projection -> `prepare_inbox` -> `load_quarantine` -> tile store from the same parsed document), every typed error routed to `_config_error` (exit 2, nothing written). Verified end-to-end against the real CLI: absent inbox is created and exits 0; an undecodable `.fit` exits 1 and records a quarantine entry keyed by content hash; the next drain exits 0 reporting it quietly; `--retry-quarantined` re-attempts; `--retry-quarantined` with a SOURCE exits 2; invalid TOML exits 2 with exactly one message.
- 4.2 (TESTING GOTCHA): a spy on `cli.load_settings_document` CANNOT see reads made by `tiles.load_tile_settings`, because `from x import y` binds per importing module. The parse-once test must spy `fitdocs.settings.load_settings_document` (the source binding) or every module that binds it, or a third settings read goes undetected.
- 4.2 (SUITE HYGIENE): CLI drain tests exercise the real `settle()` with no `sleep` seam, so each paid the default 2s interval and the suite went 18s -> 42.8s. Every real-drain CLI test now writes `settle_seconds = 0` into its `fitdocs.toml` (a supported, documented value that performs no wait — Req 4.4, pinned by task 2.2). Suite is back to ~6s. ## Post-Implementation Follow-Ups (from the feature-level validation gate)

These were found by the GO/NO-GO gate after all 14 tasks landed. None blocked the gate. Each needs a human decision because each would change behavior or contract beyond the approved spec.

- **RECOMMENDED FIX — unguarded `save_quarantine` in `drain` is the one path where completed work is reported nowhere.** `sync.drain`'s final `if record_changed: save_quarantine(data_root, record)` is unguarded, and the CLI only handles `QuarantineError` from the *read* side. With `<data-root>/.fitdocs/` unwritable (or a full disk) and a source-level failure to record, the run dies with a raw `PermissionError` traceback **after documents were already written** — no drain report, no load pass, no summary, and the user cannot see what succeeded. This is asymmetric with the feature's own stated posture ("Operation is warn-and-continue"): a failed *move* gets its own note channel and the run still succeeds, but a failed quarantine *save* takes down the whole run. No requirement mandates handling it and the precondition is unusual, which is why the gate did not block. Suggested shape if adopted: catch `OSError` around the save and report it through a note channel (or a warning) rather than propagating, so the drain report still prints.
- **Design-doc drift (harmless, worth a one-line fix each):** design.md's Allowed Dependencies still says `inbox` does not import `settings`, but `InboxSettingsError` subclasses `SettingsError` — matching the shipped `TileSettingsError` / `PluginSettingsError` precedent, introducing no cycle, and preserving the stated rationale (`load_inbox_settings` still reads no file). Also design.md's Modified-Files line promises an `InboxOutcome` contract that exists nowhere in code, tests, or design's own Components section.
- **`move_processed`'s absolute-return rationale is now stale.** design.md justified the absolute path with "`moved` is a count row" — task 4.1 subsequently made `moved` a per-file detail listing. The absoluteness was never revisited, so `Moved:` is the only channel printing absolute paths while every other channel prints inbox-relative labels. Also `Moved:` names *destinations* while `Move failures:` names *sources*, so the two disposition channels cannot be joined by label.
- **`InboxNote.detail` convention diverges across its three producers.** `settle` and the drain's read-probe prefix `"<rel>: "` into `detail`; the quarantined and move-failure producers do not. Since `_report_drain` prints subject then detail, deferred entries print the filename twice.
- **`prepare_inbox` is production-dead** after task 5.2's `validate_inbox_paths` / `create_inbox_paths` split — only tests call it. `InboxPaths`' docstring still attributes creation to it, and the public `validate_inbox_paths` returns the private `_ValidatedInboxPaths`.
- **`quarantine_version` is stamped on write but never inspected on load** — a future format change has no version gate to hang off.
- **PRE-EXISTING, not introduced here:** `_report` (and therefore `_report_drain`, which inherits its conventions) passes `markup=False, highlight=False` but not `emoji=False`, so a detail containing `:end:` renders as an emoji — mangling the instructive "add the missing marker" message. Reproduces identically on the explicit-source path. The new deferred/quarantined/move-failure detail lines are now also exposed to it.
- **PROCESS:** running mutation-capable validators in parallel let one mutate `src/fitdocs/sync.py` in the live working tree while another was running the suite, corrupting several of its results with unrelated failures. Serialize validators that mutate, or require every one of them to mutate only a scratchpad copy.
